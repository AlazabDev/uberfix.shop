# تنظيم الباك اند: بابان فقط — REST للتطبيقات و MCP للوكلاء

## الفكرة
اقتراحك صحيح، وسأضيف عليه تحسينًا واحدًا مهمًا: البابان يكونان **واجهات رقيقة** فوق
**نواة أعمال واحدة**، حتى لا يتكرر منطق الصيانة في مكانين ويحدث انحراف بينهما.

```text
                    ┌── REST API   /functions/v1/api    (تطبيق الويب، البوتات، الاختبارات)
UberFix Backend ────┤
                    └── MCP Server /functions/v1/mcp    (وكلاء الذكاء الاصطناعي)
                                 │
                                 ▼
                    نواة الأعمال المشتركة (صيانة · كتالوج · فروع · تتبّع)
                                 ▼
                       PostgreSQL + RLS على Supabase
```

## ما يتغير

1. **`/functions/v1/api`** — باب REST الجديد والرسمي:
   - `GET  /api/health` فحص الحياة
   - `GET  /api/` وصف الباب والمسارات
   - `POST /api/` نفس صيغة الطلبات الحالية (`{channel,...}` للصيانة و`{action,payload}` للكتالوج والاستعلامات)
   - نفس المصادقة الحالية: `x-api-key` للبوتات والتكاملات، و`Authorization: Bearer` لجلسات المستخدمين، وقناة `internal` تبقى محصورة بجلسة مستخدم حقيقية.

2. **`/functions/v1/mcp`** — باب الوكلاء وحده، ولم يعد هناك مسار MCP ثانٍ داخل البوابة.
   الأدوات تُكتب في مكان واحد (`src/lib/mcp/tools/`) وتُبنى تلقائيًا، ويُنقل إليها ما هو
   موجود اليوم داخل البوابة: إنشاء طلب، حالة طلب، نقل مرحلة، إلغاء، ملاحظة، كتالوج
   الخدمات والتصنيفات، الفنيون، الفروع، أقرب فرع، عرض سعر، استعلام سريع.
   الأدوات التي تكتب أو تعدّل بيانات تُوسم كأدوات غير للقراءة فقط، وتنفّذ عبر REST
   بنفس المصادقة، فلا تتجاوز أي قاعدة أمان.

3. **المسارات القديمة تبقى تعمل** كوسيط تحويل فقط: `gateway` و`bot-gateway`
   و`maintenance-gateway` تُحوّل أي طلب إلى `/api`، مع رأس يشير إلى أنها مهجورة.
   لا حاجة لتعديل أي بوت أو تكامل خارجي في نفس اللحظة.

4. **مسارات الذكاء** `‎/ai/*` تنتقل تحت `/api/ai/*` بنفس السلوك.

5. **التوثيق** يُحدَّث ليعرض بابين فقط بدل قائمة المسارات المتشابهة الحالية.

## تفاصيل تقنية
- نواة الأعمال تُنقل إلى `supabase/functions/_shared/core/` (maintenance · bot · ai)
  ويستوردها كل من `api` و`mcp`، وتبقى مصادقة `_shared/api-consumer.ts` مصدرًا واحدًا للمفاتيح.
- `supabase/functions/mcp/index.ts` مُولّد تلقائيًا من `src/lib/mcp/` — التعديل يتم في المصدر فقط.
- `config.toml`: `api` بـ`verify_jwt = false` والتحقق داخل الكود كما هو اليوم؛ `mcp` يبقى كما هو.
- لا تعديل يدوي على ملفات الترحيلات، ولا تغيير في الشيما أو سياسات RLS في هذه الخطوة.
- نشر واختبار فعلي بعد التنفيذ: صحة `/api/health`، كتالوج بمفتاح صحيح، رفض مفتاح خاطئ،
  رفض `internal` بدون جلسة، و`initialize` + `tools/list` + نداء أداة على `/mcp`.

## خارج النطاق
لا تغييرات في الواجهة أو الشاشات، ولا في منطق الصيانة نفسه — فقط تنظيم الأبواب.
